# OPD Saathi — AI-Powered Government Hospital Queue & Navigation System

Build a complete, functional, visually impressive web application for HackCache ’26. The problem statement is **Smart Queue Management and Accessible Navigation for Government Hospitals**.

Do not create only a landing page, static mockup, or project proposal. Build the actual application with working navigation, interactive features, realistic sample data, and a complete patient journey.

## 1. Product vision

OPD Saathi helps patients at a government hospital register in their preferred language, obtain a digital OPD slip, understand their queue position, find the correct room, and know when their turn is approaching.

The application must be especially easy for elderly people, people with disabilities, people who speak Hindi rather than English, and people unfamiliar with smartphones.

Use a fictional hospital named **City District Hospital**. All patients, doctors, tokens, and queue information must be simulated.

## 2. Technology and implementation

- Use React, Vite, Tailwind CSS, and JavaScript.
- Use React Router for navigation.
- Use localStorage to preserve demo data after refreshing.
- Synchronize updates between browser tabs using BroadcastChannel and storage events.
- Do not require a backend, authentication, or paid APIs for the initial version.
- Organize code into reusable components and separate hospital data, department data, and translations.
- Every visible button must perform its stated action.
- Prioritize a reliable working application over excessive animations or unnecessary features.

## 3. Visual design

Create a premium healthcare interface that feels like a real, thoughtfully designed public-service product.

Design direction:
- White backgrounds with deep navy and teal accents.
- Clear typography, generous spacing, rounded cards, subtle shadows and consistent icons.
- A calm, reassuring tone.
- Large, readable text and obvious primary actions.
- Mobile-first layout that works at 360px wide, as well as on laptops and TV screens.
- Strong colour contrast, visible keyboard focus, accessible form labels and buttons at least 56px tall.
- Avoid generic template styling, excessive gradients, unnecessary decorative graphics and clutter.

The result should look polished enough for a national-level student hackathon presentation.

## 4. Home screen

Create a welcoming home screen with the hospital name and four large actions:

1. Register
2. I Have My Slip
3. Find a Place
4. Emergency

Allow the user to choose English or Hindi, displaying the language names in their own scripts: English and हिंदी.

Include an accessibility settings option for larger text, high contrast, read-aloud assistance and avoiding stairs.

## 5. Patient registration

Build a simple, guided registration flow with one question per step and a progress indicator.

Collect:
- First name
- Age
- Gender
- Optional mobile number
- Required department

Use large department cards with plain-language descriptions:

- General Medicine — fever, cough, blood pressure and diabetes
- Children
- Women and Pregnancy
- Bones and Joints
- Ear, Nose and Throat
- Eyes
- Skin

Include Back and Continue buttons that preserve previous answers.

Add a “Someone is helping me” assisted mode with larger text and read-aloud support.

Where browser speech recognition is supported, provide a microphone input option. Otherwise, allow normal typing without errors.

Show emergency warning signs before registration. Explain clearly that anyone with serious symptoms should go directly to Emergency without waiting for a token.

## 6. Digital OPD slip

After registration, generate a unique token such as MED-042.

Display:
- Token number in very large text
- Patient's first name
- Department
- Doctor's name
- Room and floor
- Number of people ahead
- Estimated waiting time
- Clear next steps

Provide functional Print and Read Aloud actions. Include a QR code if it can be implemented reliably, but never make QR scanning essential.

## 7. Smart queue management

Create a working queue system for each department.

Patients must be able to view:
- Their token
- Number of people ahead
- Current token being served
- Doctor availability
- Estimated waiting time
- Instructions about where to go next

Calculate estimated waiting time using the number of people ahead multiplied by the department's average consultation time, plus any doctor delay. Round the result to the nearest five minutes and label it as an estimate.

When three people are ahead, show a prominent notification on the patient screen. Use browser sound, vibration and notifications only when supported and permitted.

When the staff member calls the patient's token, immediately update the patient screen with a clear message and directions to the correct room.

## 8. AI hospital assistant

Build a useful AI-powered hospital assistant that helps patients:
- Understand registration steps.
- Identify the appropriate department for their stated non-emergency reason for visiting.
- Find wards, laboratories, pharmacies and consultation rooms.
- Understand their OPD slip.
- Receive simple guidance in English or Hindi.

Ground its answers in the fictional hospital directory and approved hospital FAQs. Keep responses short and easy to understand.

**AI must be meaningful, not decorative.** If a real AI API is available, connect it securely. Do not expose secret API keys in browser code. If no API is configured, implement a clearly identified rule-based fallback and never pretend it is a live AI model.

The assistant must not diagnose illnesses, prescribe medication, determine emergency priority or tell someone with potentially serious symptoms to wait.

## 9. Hospital navigation

Create a fictional three-floor hospital with an interactive floor plan.

Ground floor:
- Main entrance
- Registration
- Help desk
- Emergency
- Pharmacy
- Laboratory
- X-ray
- Toilets
- Drinking water
- Wheelchair point
- Lift, stairs and ramp

First floor:
- General Medicine: Rooms 1 and 2
- Children: Room 3
- Women and Pregnancy: Room 4
- Bones and Joints: Room 5
- ENT: Room 6
- Eyes: Room 7
- Skin: Room 8
- Waiting hall

Second floor:
- Ward 4: Medicine
- Ward 5: Surgery
- Ward 6: Children
- Nurses' station

Patients must be able to select a destination and receive:
- A floor-plan view
- A highlighted route
- Simple, step-by-step directions
- Visible landmarks
- An option to avoid stairs
- A Listen button where speech synthesis is supported

Use a graph-based shortest-path algorithm such as Dijkstra's algorithm. Routes must use defined connections between locations, including lifts and ramps for accessible routes.

Add an “I'm Lost” button that directs the patient to the nearest help desk.

## 10. Emergency handling

Emergency access must be visible on every screen, including before registration.

Show:
- Clear directions to Emergency/Casualty
- Indian emergency number 112
- Ambulance number 108
- A message telling the patient to seek immediate help from hospital staff

Display warning signs such as chest pain, difficulty breathing, heavy bleeding, fainting, sudden weakness, serious injury, pregnancy with bleeding or severe pain, and a seriously unwell child.

Add an “I Need Urgent Help” action that immediately creates an urgent flag on the staff dashboard.

Urgent flags must remain prominent and produce an alert until acknowledged by staff.

The application must never decide who qualifies as an emergency. Qualified medical staff assess urgent cases. Emergency care must never depend on registration, a digital token or the normal queue.

## 11. Hospital staff dashboard

Create a functional staff dashboard at `/staff`.

Display each department's:
- Current token
- Waiting count
- Estimated wait
- Doctor status
- Queue condition

Implement buttons for:
- Call Next
- Mark No-Show
- Move Patient to End
- Transfer Patient to Another Department
- Update Doctor Status

Show urgent flags prominently at the top.

Include demo controls to add 20 fictional patients and reset the demo data with confirmation.

Clearly state that real-world deployment would require secure staff authentication and proper hospital integration.

## 12. Waiting-room display

Create a separate `/board` screen suitable for a hospital TV.

Show the token currently being served in each room, the next three tokens, and any delays.

Keep the display readable from a distance. Do not display patient names or private information.

Provide English and Hindi announcements using browser speech synthesis where available.

## 13. Accessibility and language

Implement English and Hindi throughout the application.

Changing the language must update navigation, buttons, forms, department names, emergency warnings, directions, notifications and waiting-room announcements.

Implement:
- Large text
- High contrast
- Read-aloud support
- Keyboard navigation
- Screen-reader labels
- Assisted registration
- Avoid-stairs routing

Do not rely on colour alone to convey queue status.

## 14. Functional requirements

The following workflow must work from beginning to end:

1. Register a fictional patient.
2. Generate a token and OPD slip.
3. Show the correct department and room.
4. Calculate the waiting time.
5. Display the patient in the staff dashboard.
6. Call the next token from the dashboard.
7. Update the patient queue screen and waiting-room board.
8. Raise an urgent flag and display it on the staff dashboard.
9. Navigate to the destination using the hospital floor plan.
10. Preserve data after a page refresh.

The patient screen, staff dashboard and waiting-room board must synchronize across tabs in the same browser.

## 15. Build priorities

Build in this order:

**Priority 1:** Complete visual design, home screen, patient registration, token generation, queue tracking and staff dashboard.

**Priority 2:** Hospital floor plans, step-by-step navigation, avoid-stairs routing, English/Hindi translations and emergency handling.

**Priority 3:** AI assistant, waiting-room board, accessibility settings and demo controls.

Keep all existing working features intact while completing later priorities.

Build the actual application now. Do not stop after creating a plan or landing page. Ensure that the main patient journey works, the UI is polished, the core buttons function, and there are no broken routes or blank screens.

When finished, briefly report which features are implemented, which are simulated, and anything that remains incomplete. Never claim that an unimplemented feature is working.
